## Engineering choices made while building

Numbered for `docs/DECISIONS.md` (WM.E256 to WM.E268). Each is Claude Code's choice inside the stage's scope.

1. **The rounding** (above): 6 decimals when the summary is built; the golden hashes of five configurations rewritten; the a5a comparison against the rounded golden value; the check of the other outputs found nothing else.
2. **The streams.** `world:pair_fluents` and `world:pair_initial` follow `world:place_event_types` in `STREAM_NAMES`. Nothing is drawn from `world:pair_fluents` in this stage; the initial pairs come from `world:pair_initial`, fluent by fluent in label order. A world without an event file that defines pair fluents draws from neither, so its definition, identity, and every file but `config.yaml` (which lists the two new seeds under `provenance.stream_seeds`) are those of stage c1.
3. **`pair_fluents.py`.** `PairFluent(label, index, symmetry, functional, initial_rate, total=False)` and `PairFluents(fluents, initial_pairs)`, the initial pairs one Boolean matrix per fluent with the entities as rows and the fluent's targets as columns (entities now; places for a location fluent in c3, where the matrix is `(entities, places)`), so that c3 adds the second kind of target and nothing else. The event file's `pair_fluents` block must label its entries `PAIRFL.1` to `PAIRFL.k` without a gap (the specification numbers the pair fluents between entities first); `total: true` is refused until c3, and so are a `place_event_types` entry and a `locations` key. The initial pairs follow the specification's procedure in a fixed draw order: for a functional pair fluent one draw against the rate per entity in entity order, then the partner uniformly among the entities that keep the profile (an entity whose row was already filled by an earlier partner's draw, in a symmetric functional pair fluent, or with no eligible partner, gets none); otherwise one draw per unordered pair (`i < j`, row by row) for a symmetric or an asymmetric pair fluent, with one more draw (`rng.integers(2)`) for the direction of an asymmetric pair, and one draw per ordered pair (row by row) for a general one. A rate of 0 draws as the others do and selects nothing, so that c2b's draws are uniform whatever the rates. `initial_pairs.csv` has the columns `pair_fluent`, `first`, `second`: one row per ordered pair that holds, both directions of a symmetric pair, by pair fluent, then by first and second in entity order. `profile_violations(fluent, matrix)` is the one check of a profile, which the generator, the loader, and the runtime share.
4. **The definition.** The symbol kind `pair_fluent` (`label`, `kind`, `derived` false, `fluent` true, `arity` 2, `symmetry`, `functional`, `total`, `initial_rate`, all hashed) after the numeric fluents and before the event types, as the fluent-like symbols stand together. The literal table holds the entity-scope literals `pair_some` and `pair_someof` (role null, `pair_fluent`; keys `SOME.PAIRFL.k` and `SOMEOF.PAIRFL.k`) where a derived fluent's rule reads them, after the numeric thresholds in the group order, computed before the matrices from the state's pairs as the fluent and numeric threshold literals are. The pair literals of preconditions and conditions live in the event-type records with the same four kinds, as the Boolean and numeric precondition literals do (they are judged per binding outside the matrices); the loader accepts all four kinds in the table (the two-argument kinds with the role `binding` and the roles `first` and `second`), so that a definition that lists them is well formed. A precondition pair literal's record is `{kind, pair_fluent, first, second, value}` or `{kind, pair_fluent, role, value}`, with `origin: profile` for a compiled literal and no `origin` key otherwise; a Boolean or numeric literal has no `kind` key, so a reader tells them apart by it. A pair effect's record is `{kind: pair, pair_fluent, first, second, value, expression}`, with `condition` as any effect. A pair condition literal's record is the precondition form, its `kind` one of the four beside `feature`, `fluent`, and `numeric`.
5. **`PairLiteral` and `Effect.second`.** `dynamics.py` gains `PairLiteral(kind, pair_fluent, first, second, value, origin)`, whose `role` and `fluent` properties name the first role and the pair fluent so that code that counts literals by role (`world_stats`) reads it as the other kinds, and `Effect.second`, the second role of a pair effect (`Effect.pair`). The event-file parser replaces each pair literal's text with a placeholder name before the taxonomy's expression parser runs, because the parentheses and the comma of `PAIRFL.1(agent, patient)` are not in the expression grammar, and maps the placeholders back when it visits the parsed expression; `parse_condition` recognizes a pair literal by its form.
6. **What a pair literal names, and achievability.** For the rules of "Preconditions", "Effects", and "Conditions (F5)", a literal names a pair (both directions of a symmetric pair fluent are one pair), the row of a role (`SOME`; `SOMEOF` of a symmetric pair fluent names the same set), the column of a role (`SOMEOF`), or the rows of both roles (`SAME`). Two literals that name the same thing with different values contradict, and the same thing twice is a duplicate; two effects on one pair with different values contradict, and with the same value are a duplicate; an add whose precondition requires the pair, or a delete whose precondition requires its absence, changes nothing; a pair condition literal names no pair or row the precondition names (the rule read exactly: a condition that another literal entails without naming the same pair or row is allowed), nor the pair the effect itself writes (as a Boolean condition never names the fluent the effect sets: with the condition true the effect changes the pair, with it false the pair already has the value, so the condition would be a condition in name only). Achievable: a positive literal when its pair fluent's initial rate is above 0 or some effect adds a pair of it; a negative one when the rate is below 1 ("some initial state lacks it"), the pair fluent is functional (every other pair of a row is absent), or some effect deletes one; `SAME` on a symmetric functional pair fluent is never achievable, because two entities with one partner would give that partner two partners. For an explicit entry each rule is a `ConfigError` naming the file and the entry; `check_dynamics` checks the same rules on any definition and raises a `ValueError` naming the event type, as it does for the Boolean rules.
7. **Compiled literals.** `compile_profile_literals` appends the compiled literals (F4) to every event type with an unconditional add effect after the fix-ups and before the conditions are drawn, in effect order (`NOT PAIRFL.k(second, first)` for an asymmetric pair fluent, `NOT SOME.PAIRFL.k(first)` for a functional one, and `NOT SOME.PAIRFL.k(second)` too for a symmetric functional one), each with the origin `profile`, a literal already present by what it names (whatever its origin) not added twice. An explicit entry whose compiled literals contradict its precondition is an error naming the file and the entry, and a pair condition of an explicit entry is checked against the compiled literals as against the precondition. `redraw_preconditions` keeps the compiled literals of an event type whose own literals are drawn again, and `check_dynamics` requires every add to carry them. A conditional add on an asymmetric or functional pair fluent is refused in an event file (c2b redraws it).
8. **The runtime.** `State.pairs` is a tuple of Boolean matrices, one per pair fluent in symbol order, read-only, with an empty diagonal; `State.from_true` takes the pairs as `[pair fluent, first, second]` triples (the definition's initial pairs when None), and `pairs_record` gives them back in the order of `initial_pairs.csv`. A definition that carries no initial pairs (a fixture's, whose initial pairs come apart from the record) starts with none. `derive` fills the `pair_some` and `pair_someof` literals from the state's pairs before the entity layers; `pair_literal_holds` judges the four kinds over a bindings array (a symmetric pair fluent holds both directions of every pair, so a literal about it reads both without a special case). The facts an event reads and writes are keyed `(entity, fluent)` for a base fluent and `(pair fluent, first, second)` for an ordered pair: a pair effect writes its pair and, for a symmetric pair fluent, the reverse; a `pair` literal reads its pair (both directions when symmetric), `SOME` every pair of the row, `SOMEOF` every pair of the column, `SAME` every pair of both rows, rows and columns ranging over every entity of the definition (not only an episode's participants, which the runtime does not know), and a literal on a derived fluent reads, through `RuntimeDefinition.pair_cone`, the rows and columns of the entity its rule reads, directly or through other derived fluents, beside the base fluents of `cone`. `apply` writes the pairs of the fired effects into copies of the matrices and then checks every profile; a violation is `ProfileViolationError` (kind `profile`), naming the pair fluent, the pairs that hold, and the events. The error kinds of the fixtures stay `illegal` and `interference`.
9. **The `spatial` block.** The event file's block is checked for its form (a pair fluent of the file's `pair_fluents` block, a `detector` name, a `parameters` mapping of numbers or strings) and written last in `definition.json` as `spatial` with `spatial_id`, the SHA-256 of its canonical JSON; both are absent without a block, and neither is hashed into the rule-set identity. The loader checks the form and the identity (a wrong `spatial_id`, a block without its identity, an unknown pair fluent, or a malformed entry is a `DefinitionError`) and keeps both on `RuntimeDefinition`.
10. **Episodes and histories.** An episode's initial state holds the initial pairs among its participants and no other pair (WM.38: "an episode keeps the pairs among its participants"), so that a history's `initial_pairs` (every ordered pair that holds among the participants, both directions of a symmetric pair, as triples, after `initial_numeric`) is the whole pair part of the episode's initial state, and `replay` builds the state from it without the definition's initial pairs. Under `scene.initial: redraw` the pairs are drawn again among the participants, in entity order, by the initial-pair procedure at each pair fluent's rate, after the Boolean and numeric redraws, so the participants and the Boolean and numeric redraws of an episode are those of the same world without pair fluents. A pair change is `{"pair", "first", "second", "to"}`, one per pair effect whose fired write changed the value, in the direction the effect names (`pair_changes_of`); `replay` checks every event's pair changes against the same function, and refuses a history without `initial_pairs` on a world with pair fluents. A world without pair fluents writes neither key, and its histories are byte-identical to stage c1's.
11. **The evaluator and the fixtures.** `BruteForce` reads the pair part of a state as sets of label pairs (`BrutePairs`, set with `with_pairs` as the numeric part is with `with_numeric`), never through the matrices: the pair literals of rules, preconditions, and conditions, the pair effects (both directions of a symmetric pair), the read and write sets with rows and columns over every entity, and the profiles after a step (`check_profiles`). The fixture format gains `initial_pairs` after `initial_numeric` and `pairs` after `numeric` in each step, both lists of triples in the order of `initial_pairs.csv`; `check_fixture` and `check_fixture_brute` compare them; `generate_fixture` takes `initial_pairs`; the version stays 1. The hand world gains three pair fluents (`PAIRFL.1` symmetric, `PAIRFL.2` asymmetric, `PAIRFL.3` symmetric functional, every initial rate 0), a derived fluent `BOOLFL.4 = SOME.PAIRFL.1`, and five event types able for every ordered pair (`EVENTTYPE2.2`, a symmetric add; `EVENTTYPE2.3`, a delete that needs the pair; `EVENTTYPE2.4`, an asymmetric add with its compiled literal; `EVENTTYPE2.5`, a functional add with its two compiled literals; `EVENTTYPE2.6`, a pair condition); `hand_29` to `hand_37` are fixtures 1 to 4, 10, 12 to 14, and 16 of the specification. The earlier hand fixtures gained `initial_pairs: []`, `pairs: []` after each step, the new symbols and event types in their definitions, and the new event types' legal bindings; `test_quiescence_ends_an_episode` lists the new always-legal event types among those it removes. The tiny fixtures did not change (`make-fixtures` on `data/world/tiny.yaml` gives the committed files byte for byte).
12. **The corpus, the statistics, and the command line.** `load_world` refuses a world with pair fluents with a `CorpusError` that names stage c4. `world_stats.yaml` counts a pair condition literal under `condition_literals.by_symbol.pair` only when the world has one, so that a world without pair fluents writes its statistics as before; `absorbing_fluents` and `enabling_edges` leave pair effects out, and `episode_stats` counts Boolean changes only (the pair statistics are c2b's). The `define` line names the pair fluents only when there are any, so the snapshot's quick-start figure did not move.
13. **The example world.** `data/world/events/pair_example.yaml` defines four pair fluents (symmetric, asymmetric, general functional, and asymmetric functional with the rate 0, so one has no initial pairs) and five explicit event types over them with every kind of pair literal, adds and deletes, and two pair conditions (`SOME` and `pair`), each with the explicit requirement `TRUE`, which keeps the constraints of the features defining at the parent (WM.E106), so that every event type occurs in the statistics episodes (`EVENTTYPE2.2.1`, the `SAME` chain, in about one step in a thousand); `data/world/tiny_pairs.yaml` uses it with the tiny world, places kept. It is the world of the acceptance checks.

## File formats added

- **`initial_pairs.csv`** (a world with pair fluents): columns `pair_fluent`, `first`, `second`; one row per ordered pair that holds at `TIME.1`, both directions of a symmetric pair, by pair fluent in label order, then by first and second in entity order. Read by `load_definition` beside `entities.csv` and `places.csv`, and required when the definition has pair fluents.
- **`definition.json`**: the symbol kind `pair_fluent`; the literal kinds `pair_some` and `pair_someof` (and, accepted, `pair` and `pair_same`); pair literals in `precondition.literals` and in `condition.literals` (`kind`, `pair_fluent`, `first` and `second` or `role`, `value`, `origin` when compiled); pair effects (`kind: pair`, `pair_fluent`, `first`, `second`, `value`, `expression`); `spatial` and `spatial_id` last, only with a block.
- **Histories**: `initial_pairs` after `initial_numeric` (a list of `[pair fluent, first, second]` triples, `[]` when none holds), and pair changes `{"pair", "first", "second", "to"}` among an event's `changes`; a world without pair fluents writes neither.
- **Fixtures**: `initial_pairs` after `initial_numeric`, and `pairs` after `numeric` in each step, in the form of the histories' `initial_pairs`; the version stays 1. `tests/fixtures/world/README.md` has a "Pair fluents (stage c2a)" section with the semantics operation by operation, and says that the total functional replacement comes in c3.
- **The event file**: the `pair_fluents` block (`PAIRFL.<n>: {symmetry, functional, initial_rate}`), pair literals in `precondition` and in a `when ... then` condition, pair effects (`PAIRFL.<n>(agent, patient) := 0 | 1`), and the `spatial` block (`PAIRFL.<n>: {detector, parameters}`).
- **`config.yaml`** of every world: the seeds of `world:pair_fluents` and `world:pair_initial` under `provenance.stream_seeds`.

## Open questions

None of these changes the design; each is recorded for Jon's eye.

1. **The literal table and the four kinds.** "Literals over pairs" says the four kinds join the literal table. As built, the table holds the two entity-scope kinds (`SOME` and `SOMEOF` of the entity itself, which rules read), and the records of preconditions and conditions hold all four, as they hold the Boolean and numeric literals; the loader accepts all four in the table. If the Rust runtime is better served by every pair literal in the table (with the role `binding` and the two roles), the builder can add them without changing the records, at the cost of an identity change for worlds with pair fluents.
2. **The rule that a condition names no pair or row the precondition names** is read exactly. Under a symmetric pair fluent a condition can be entailed by the precondition without naming the same thing (`PAIRFL.1(agent, patient)` in the precondition and `SOMEOF.PAIRFL.1(patient)` in the condition: the condition is always true), and is allowed. An entailment check would be a larger rule; c2b's draws could redraw such a condition by the same exact rule, or by a check of what the precondition entails.
3. **`SAME` on a symmetric functional pair fluent** is never satisfiable (two entities with one partner give that partner two), so it is refused as unachievable. The specification does not say so; c2b's draws should never draw it, and the default profiles (`functional_rate` 0.25, equal symmetries) would draw a symmetric functional pair fluent for about one pair fluent in twelve.
4. **A pair condition on the pair the effect writes** is refused, by analogy with the Boolean rule ("the condition never names the fluent the effect sets"). The specification lists the rule for Boolean conditions only.
5. **Negative achievability** is read as an initial rate below 1, a functional pair fluent, or some delete. A general pair fluent with the rate 1 and no delete has every pair at `TIME.1` and forever, so a negative literal on it is never true; an asymmetric one with the rate 1 has one direction of every pair, so a negative literal on it is true half the time, which the reading counts as achievable only through the rate (1 is not below 1): such a literal is refused. A rate of 1 is an odd setting; the reading errs on the side of refusing.
6. **Rows and columns range over every entity of the definition**, not only the participants of an episode, for non-interference. Within an episode only pairs among participants can be written, so the two readings give the same verdict; the wider one costs nothing and needs no knowledge of the episode in the runtime.
7. **The redraw draws the participants' pairs in entity order**, not in the order the participants were drawn (the Boolean and numeric redraws go in drawn order). Either order is deterministic; entity order matches the procedure of the initial pairs, which is defined over the entities in order.
8. **A history's `initial_pairs` lists both directions of a symmetric pair.** The specification's example shows one triple for `PAIRFL.3`, whose profile it does not give. Listing every ordered pair that holds makes the list the pair part of the state, as `initial` lists every true fluent; the changes record a symmetric pair once, as the specification says.
9. **The taxonomy's scalar values at full precision** in `entities.csv` and `places.csv` (c1's open question 1) remain as they were: the check of item 1 covered the YAML and JSON outputs, which Jon's Linux run compared, and found nothing else.
10. **An explicit requirement `TRUE` keeps the parent's constraints** (WM.E106), so the example world's "always able" event types are able for the pairs of their parent's base relation. The comment of `pair_example.yaml` says so. A world in which every pair is able would need a parent without defining features, which no event file can give.
11. **The corpus's refusal and the default configurations of c2b.** The refusal (item 12 of the stage) is right for this stage: no corpus states a fact its oracle cannot check. But "Configuration" of the specification gives `data/world/default.yaml` 4 pair fluents and `data/world/tiny.yaml` 2 in stage c2b, and the tiny and default corpora name those worlds, so from c2b until c4 (which extends the oracle to pairs) the corpora could not run on their own worlds unless c2b keeps the pair settings out of `tiny.yaml` and `default.yaml` (in configurations of their own, as this stage's `tiny_pairs.yaml`), or the corpus of c2b and c3 runs on a world whose pair fluents it ignores. The second would state nothing false (the corpus reads no pair), but its scenes would hold pair changes its oracle does not replay. This is a question for the c2b session's prompt, not a change to this stage.

## Notes for stage c2b

What the builder of the generation of pair fluents (drawn profiles, initial rates, pair literals in preconditions, pair effects, `pair` conditions, derived rules over `SOME` and `SOMEOF`, the quotas, and the statistics) must know:

1. **The configuration block `pair_fluents`** of the specification (`count`, `symmetry`, `functional_rate`, `initial_rates`, `literal_kinds`, `same_rules`, `derived_rules`, `rule_weight`, `fluents`) and the shares `event_types.preconditions.pair_share`, `event_types.effects.pair_share`, and `condition_kinds.pair` are not read yet: `config.py` is untouched. `generate_pair_fluents(entity_count, streams, explicit, explicit_source)` in `pair_fluents.py` builds the pair fluents from the event file's block alone; c2b draws `count` profiles and rates from `streams.pair_fluents` first, in label order, and lets a `fluents.PAIRFL.<n>` override or an event file entry replace a draw (the event file's labels must then be among `PAIRFL.1` to `PAIRFL.count`, as `fluents.BOOLFL.<n>` must be among the fluents). The initial pairs already come from `streams.pair_initial` by the specification's procedure (`draw_initial_pairs`), and a rate of 0 draws as the others do.
2. **The dynamics.** `_Dynamics` in `event_types.py` takes `pair_fluents`; `produced()` and `achievable()` leave pair effects out, `literal_achievable` and `_condition_literal_achievable` judge a `PairLiteral` by `pair_literal_achievable(literal, fluent, adds, deletes)` (`pair_adds_and_deletes()` gives the sets), `_literal_slot` keys a precondition literal by what it names, `condition_keys` does not cover pair literals (a Boolean literal can never name a pair fluent), and `compile_profile_literals` runs for every draft after the fix-ups: c2b's drawn pair literals and effects go into `draw_preconditions` and `draw_effects` as replacements at the shares from `world:pair_preconditions` and `world:pair_effects` (the pattern of the numeric streams, WM.E193), before `compile_profile_literals`; a drawn add whose compiled literals contradict the precondition, a contradiction, an empty effect, an unachievable literal, and a conditional add on an asymmetric or functional pair fluent are redrawn where the explicit checks raise. The checks of an explicit entry are `_check_explicit_pair_literal`, `_check_explicit_pair_effect`, and `_check_pair_condition_against`; `check_dynamics` (`_check_pair_effect`, `_check_pair_condition_literal`) is the invariant checker for both. `redraw_preconditions` keeps compiled literals; a redrawn own literal could be a pair literal in c2b, drawn from a part of `world:pair_preconditions`.
3. **Derived rules.** A rule reads `SOME.PAIRFL.k` or `SOMEOF.PAIRFL.k` as an input key; `build_definition` turns it into a `pair_literal_spec` and `pair_literal_key_of_rule_input` recognizes it. `fluents._draw_rules` and `_inputs` do not offer pair literals in the pool yet: c2b adds them with the weight `pair_fluents.rule_weight`, the quota `derived_rules` first, and the values for `derived_initial_values` from the initial pairs (`PairFluents.initial_pairs`), which `entity_literal_values` already takes (`pairs=`). The runtime's `derive`, `pair_cone`, and the evaluator's `pair_cone` already read such rules; the hand world's `BOOLFL.4` exercises them.
4. **The statistics.** `world_stats.yaml` has no `pair_fluents` block yet; `world_stats` counts a pair condition literal under `by_symbol.pair` only when there is one, and `episode_stats` counts Boolean changes alone. The specification's block (pair fluents by profile, initial rates and pairs, pair literals by kind and role, compiled literals by origin, pair effects by value, pair conditions, and the episodes' pair changes per event) is c2b's, as is `figures.py`'s reading of it and the off settings of "Determinism" (`pair_fluents: {count: 0, locations: 0}`, and the pair shares at 0) with their baselines in the snapshot.
5. **The fixtures.** `fixture_initial_pairs(definition)` gives a built definition's initial pairs; `world_fixtures` passes them, so `make-fixtures` on a world with pair fluents already writes `initial_pairs` and `pairs`. The tiny world's committed fixtures gain pair fluents when `data/world/tiny.yaml` gets its `pair_fluents` block in c2b (the specification: 2 pair fluents between entities, 1 location fluent in c3).
6. **The state's pair part** is a tuple of `(entities, entities)` matrices; `profile_violations` handles a non-square matrix for the total profile already, and `_check_state` checks the square shape, which c3 relaxes for a location fluent's `(entities, places)`.
7. **Labels.** `PairFluent.index` is the number in the label; `pair_label(i)` makes it. The pair fluents between entities are numbered first (WM.54), so c3's location fluents take the numbers after `count`.
8. **The corpus** refuses a world with pair fluents in `load_world`; the refusal stays until c4 extends the oracle's replay, and the tiny corpus's world must keep no pair fluents until then, or c2b's `tiny.yaml` change breaks the corpus tests. Either c2b leaves `tiny.yaml` without pair fluents and gives the pair settings to a `tiny_pairs.yaml` of its own, or c4 comes first for the corpus; this stage's `data/world/tiny_pairs.yaml` is the natural home of the tiny pair settings until c4.
