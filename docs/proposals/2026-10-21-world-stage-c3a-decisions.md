7. **The tests, the documents, and the check list.**

### Reading of the scope

- **"A world without location fluents has none of the new keys."** Every new key of `definition.json`, `entities.csv`, the histories, and the fixtures is written only when the world has a location fluent, and a place event type without dynamics keeps its stage c1 record byte for byte, so every configuration of `data/` except the chain example's keeps its stage c2b identity; `config.yaml` alone gains the seed of `world:habitats`.
- **"Every draw of this stage happens only in a world with location fluents."** The habitat draws, the redraw of places, and the draw of extra places happen only with location fluents, so the episodes of every other world are unchanged.
- **"Performable when an event file gives them."** A place event type with an entry is performable (`EventTypeRecord.performable` reads the dynamics: a move has its add, an act its location literal); one without an entry stays as in stage c1, a requirement only.
- **"The entity event types of an event file may use `SAME.PAIRFL.k(agent, patient)` and `SOMEOF` on a location fluent."** `SAME` on a location fluent belongs to entity event types (two entities at the same place); `PAIRFL.k(agent, patient)` and `SOMEOF.PAIRFL.k(patient)` on a location fluent belong to place event types (the patient is the place); `SOME` of an entity on a location fluent is refused everywhere, and so is a literal that would read a place as an entity or an entity as a place.
- **Tests of the chain example's world are in the fast tier**; nothing of this stage needs a default-scale run except the regenerated snapshot figures of the existing worlds, which must not move.

## Engineering choices made while building

Numbered for `docs/DECISIONS.md` (WM.E290 to WM.E306). Each is Claude Code's choice inside the stage's scope.

1. **The configuration.** `pair_fluents.locations` may be above 0 when the world has places, and is an error with `places: null`; the location fluents take the labels after the pair fluents between entities (`PairFluentsConfig.location_labels`, WM.54); the code's default stays 0 until stage c4 (WM.63), so every configuration of `data/` but the chain example's has none.
2. **The location fluent.** A `PairFluent` with `total` true, `symmetry` `general`, `functional` true, and `initial_rate` None, written in its symbol as `initial_rate: null` (as a derived fluent's rate is null), because its initial pairs are the habitats and not a draw at a rate; `PairFluent.rate` gives 0 where a number is needed; `PairFluents.between_entities` and `locations` split the two kinds; `profile_violations` skips the checks over pairs of entities for a total pair fluent, whose matrix is `(entities, places)`, so that a world with as many places as entities is judged right.
3. **The habitat draw.** `world:habitats` is created after `world:pair_conditions`; `with_location_fluents` in the new module `locations.py`, called by `define` after the pair fluents between entities, sums the requirement matrices of every place event type (drawn or explicit) into `a(x, q)`, raises `1 + a` to the habitat strength, and draws each entity's place with one weighted `rng.choice` over the places, in entity order, per location fluent in label order; strength 0 is the uniform draw, and a world without location fluents draws nothing, so it is byte-identical to stage c2b apart from the stream's seed in `config.yaml` (checked against the reference run: every file of the five worlds and the two corpora is identical but the configuration files).
4. **The location columns.** The initial places are the last columns of `entities.csv`, one per location fluent, named by its label, with place labels, written only with location fluents; `initial_pairs.csv` keeps the pairs between entities alone; the loader accepts the location columns (all or none), builds the location matrices from them beside the entity matrices of `initial_pairs.csv`, requires places when the definition has a total pair fluent and the location fluents after the others, and leaves `initial_pairs` None when a fixture gives the places apart.
5. **The forms a location fluent allows** are one rule, `location_literal_problem` in `definition.py`, shared by the loader, the event-file checks of entity entries, and the place dynamics: `PAIRFL.k(agent, patient)` and `SOMEOF.PAIRFL.k(patient)` in a place event type (the patient a place), `SAME.PAIRFL.k(agent, patient)` in an event type between entities, never `SOME` of an entity (always true), never a location fluent read as a pair of two entities or as `SOMEOF` of an entity, and in a place event type a pair fluent between entities read as `SOME` or `SOMEOF` of the agent alone. A derived rule never reads a location fluent (`pair_rule_inputs` leaves total pair fluents out; `build_definition` refuses a rule input on one).
6. **Achievability on a location fluent.** Every literal but `SOME` of an entity is achievable in both polarities: every entity is somewhere and the habitat weights are positive at every place, so two entities can share a place or not, a place can be empty or not, and an agent can be at the bound place or elsewhere. `random_pair_literal` and `random_pair_effect` draw over the pair fluents between entities alone, so the entity event types' draws never touch a location fluent.
7. **Moves and acts in the records.** A move's compiled literal has the origin `move` (`compiled_literals` returns it alone for an add on a total pair fluent) and an act's location literal the origin `act`; a literal or an effect an entry gives by what it names is kept as given, with no origin, and not added twice. Whether a place event type is a move or an act, and which location fluent it uses, is read off its effects and precondition (`EventTypeRecord.move`, `act`, `location`) rather than written as a new key, so that a performable place event type's record holds `precondition` and `effects` as an entity event type's does, with `explicit` true, and one without dynamics keeps its stage c1 record byte for byte; `performable` is true for a place event type with a precondition or effects.
8. **The place dynamics module.** `place_dynamics.py` applies the entries after the entity event types are generated (`apply_place_dynamics` in `define`, before the definition is built) and checks each entry's literals and effects against the rules, each an error naming the file and the entry; the Boolean values an agent literal may need come from the initial values and from every effect of the entity event types and of the entries; `check_place_dynamics` holds the same rules as invariants, called beside `check_dynamics`; `statistics_episodes` joins `place_able_table` to `able_table`, so that a performable place event type whose requirement holds for no binding is counted among the never-able ones.
9. **Explicit place requirements.** `place_requirement` in `requirements.py` builds one constraint over `agent.` entity literals and `patient.` place literals (or a comparison of an entity scalar with a place scalar), and `generate_places` replaces the drawn requirement with it after every requirement is drawn and before the capacities, as an explicit two-place requirement replaces an own constraint, so that the other place event types' draws do not shift; the constraint is `CONSTRAINT.PLACEEVENTTYPE.<n>.1` of the family `explicit`.
10. **The runtime.** `_check_state` requires each pair fluent's shape (`pair_targets`) and an empty diagonal for a pair fluent between entities (moved from `State.__post_init__`, which cannot tell a location matrix from a square one); `_entities_of` gives the agent alone of a place event's binding wherever derived facts are computed; `Event.from_labels`, `binding_labels`, and `describe` read and write a place label as the patient of a place event type; `_check_event` refuses an event of a place event type without dynamics as illegal; `apply_step` applies a fired add on a location fluent as the total functional replacement, and the profile check requires exactly one place per entity.
11. **The keys of non-interference.** A move writes the row of its agent, `("row", location fluent, entity)`, and `SOMEOF` of a place reads the place's column, `("place_column", location fluent, place)`, a third tag beside `row` and `column`, because a place's index space is not the entities' and a row of a location fluent always shares a pair with a place's column; `overlaps` says so; `_fact` names the place of an entity and a place's column in the error messages. The brute-force evaluator expands both into pairs, and the verdicts agree on every pair of legal events of the chain world in 200 random states.
12. **Episodes.** The three scene keys in `EpisodeSettings`, `read_scene_settings`, and the corpus's `SceneConfig`, `_read_scene`, `resolved`, and `episode_settings`, listed in `data/corpus/default.yaml`; `EpisodeGenerator(..., habitat_strength=)` (`define` passes the configuration's, `simulate` reads the run's `config.yaml`, the corpus the world's configuration) computes the habitat weights from `place_able_table` on first use, redraws the participants' places after the pair redraw (one weighted draw per participant in entity order, per location fluent), copies the seed's row to every participant under `initial_location: seed` (under `keep` and `redraw` alike, drawing nothing), draws the extra places in one draw without replacement from the places no participant is at, lists the episode's places in place order, passes them to `legal_bindings` for the place event types, and keeps a location fluent's matrix whole where the pairs between entities are restricted to the participants. The habitat strength is not written to `definition.json`, because a history replays without it.
13. **Histories and replay.** `places` after `participants`, `initial_places` after `initial_numeric` and before `initial_pairs` (the pairs between entities alone); a move records the deletion of the old place first, then the add of the new one; `replay` builds the initial state with the participants' places and every other entity at its place of the entities table, computes the Boolean and numeric changes over the agent alone of a place event (`_touched_entities`), checks every profile after every step, and refuses a history whose places do not fit the definition.
14. **The brute-force evaluator** reads a location fluent's pairs as `(entity, place)`, applies the replacement, judges the total profile, expands a move's row and a place's column, counts a place event type with dynamics as performable, accepts a place as its patient, and reads `initial_places` beside `initial_pairs`; a generated fixture's illegal event is an entity event where the state offers one, as before, so the tiny fixtures do not change.
15. **The fixture format and the hand world.** `initial_places` after `initial_pairs`, only with location fluents; a step's `pairs` lists the location pairs after the others; the version stays 1. The hand world gains two places (`PLACE.1.1` with `PLACEPROPERTY.1`, `PLACE.2.1` without it), the `place_binding` scope with the act's constraint and the three requirements, the location fluent `PAIRFL.4`, three place event types (go, a move able everywhere; rest, an act able at the places with the property, which clears `agent.BOOLFL.1`; join, a move that needs `SOMEOF` of the place), and `EVENTTYPE2.7` (meet, which needs `SAME` and sets `patient.BOOLFL.2`); `hand_38` to `hand_44` are the location fixtures, and the earlier hand fixtures were regenerated with every entity at `PLACE.1.1` (the check is below).
16. **The chain example.** `data/world/events/place_chain_example.yaml` with `data/world/tiny_place_chain.yaml` (`pair_fluents: {count: 1, locations: 1}`, every pair draw at 0, as `tiny_pairs.yaml`) is the world of the acceptance checks; `figures.py` reads it into the snapshot (world figures only, no baselines, as for `tiny_pairs`), and its run lives in `runs/world/tiny_place_chain_seed1`.
17. **The tests** (`tests/world/test_world_locations.py`, the fast tier): the configuration and the stream; the fixed profile and the hashed symbol; the location columns and the loader; the habitats over 400 seeds of `world:habitats` on the chain world's weights, each entity's share of each place within three binomial standard deviations plus one draw of its weight, with strength 0 (uniform) and with the default, the check not vacuous because some entity is able at more place event types at one place than at another; `legal` and `derive` against the brute-force evaluator in 1,000 random states; applying together against one at a time in every order on 1,000 random non-interfering sets; the interference verdicts; the replacement and the acts; 1,000 episodes under `keep` and under `redraw` with every acceptance property of the episodes and replay; the three scene keys and the order of the draws; `uniform_event_type`; the histories and their tampering; `simulate --config`; the corpus's reading of the keys and its refusal; every broken entry, one test per rule; the given literal and effect kept once; the hand fixtures; and the chain world's generated fixtures under both checkers.

## File formats added or changed

- **The configuration file**: `pair_fluents.locations` above 0 (with places); `places.habitat_strength` now used.
- **`definition.json`**: a `pair_fluent` symbol with `total: true` and `initial_rate: null` (a location fluent), after the pair fluents between entities; a performable place event type's record with its `precondition` (the `act` literal or the compiled `move` literal, origins `act` and `move`, with the entry's further literals) and `effects` (the move's add, with the entry's further effects), and `explicit: true`; a place event type without dynamics keeps its stage c1 record.
- **`entities.csv`**: one column per location fluent, named by its label, with each entity's initial place, after the numeric fluents; only with location fluents.
- **The event file**: the `place_event_types` block, `PLACEEVENTTYPE.<n>: {kind: move | act, requirement, precondition, effects, location}`.
- **Histories**: `places` after `participants`, `initial_places` after `initial_numeric`; a move's two pair changes, with a place as `second`; the patient of a place event is a place label.
- **The fixtures**: `initial_places` after `initial_pairs`; a step's `pairs` with the location pairs; the version stays 1.
- **The scene block** (both readers): `extra_places` (default 1), `places` (`episode` | `all`), `initial_location` (`world` | `seed`); the corpus's resolved `config.yaml` lists them.
- **`config.yaml`** of every world run: the seed of `world:habitats` under `provenance.stream_seeds`.
- **The snapshot**: the world `tiny_place_chain` (world figures only).

## Open questions

None of these changes the design; each is recorded for Jon's eye.

1. **The location fluent's symbol writes `initial_rate: null`** (choice 2), where the specification's symbol table has a float. The alternative, a rate of 1.0, would misname the habitat draw as a rate; the null is read as "no rate, the initial pairs are the habitats", as a derived fluent's null rate is read. The Rust runtime's reader must accept null there.
2. **The habitat strength is not in `definition.json`** (choice 12): `scene.initial: redraw` needs it, and the generator takes it as a parameter, which `simulate` reads from the run's `config.yaml`. A history replays without it, and a fixture never redraws. If the 3D runtime should redraw places, the strength could join the location fluent's symbol, at the cost of an identity change for worlds with location fluents.
3. **A place event type's kind is not a key of its record** (choice 7): a move is a place event type with an add on a location fluent, an act one with its location literal, which the runtime and the corpus can read off the record. A `place_kind` key would make the record self-describing for the Rust runtime at the cost of a hashed key.
4. **Conditions on the place's features are not supported** in a place event type's effects (choice 8): the condition literals of `dynamics.py` name `PROPERTY`, `PART`, `BOOLFL`, and `NUMFL` symbols of a role, and a place has no fluent; an act's condition reads the agent, or `SOMEOF` of the place. Stage c3b, which draws "further effects on the agent's fluents, drawn as for the other event types", must keep the feature kind of a condition to the agent, or extend the condition literals to place features.
5. **A literal or an effect an entry gives keeps no origin** (choice 7): an act whose entry writes `PAIRFL.2(agent, patient)` in its precondition has the literal without the origin `act`, by the rule that a literal already present is not added twice. The corpus states compiled literals and ordinary literals alike (ruling 5a), so nothing is lost; a reader who wants the origin regardless would have the entry's literal replaced by the marked one.
6. **The explicit requirement `TRUE` of a place event type holds for every binding** (the chain example's move), which the generator would have drawn again as degenerate; an explicit requirement is never drawn again, as an explicit two-place requirement is not, and `world_stats.yaml` reports its density 1.0 without a warning.
7. **The location statistics wait for c3b**: `pair_fluents` of `world_stats.yaml` counts a location fluent under `by_symmetry.general` and `functional`, with `initial_rate` null and `initial_pairs` the number of entities; the literals and effects of place event types are not counted under `precondition_literals` and `effects`; `two_place_share` counts a place event as two-place; and `pair_changes_per_event` counts a move's two changes.
8. **The achievability of an entity event type's literal does not see the place event types' effects** (choice 8): the entity event types are generated before the place dynamics, and `check_dynamics` reads their effects alone; an explicit entity entry whose literal only an act's effect could make true is refused as unachievable. The chain example needs no such literal. Stage c3b's drawn acts, whose effects could make a value achievable, face the same order; folding the place effects into the pool of the entity event types would change the draws of every world with acts.
9. **The `wake` event type of the chain example** reads `SOME.PAIRFL.1(agent)` (near someone) rather than `SOMEOF` of the place, which only a place event type can read; the comment of the file says so.

## Notes for stage c3b

What the builder of the generated location dynamics (drawn moves and acts, `SAME` and `SOMEOF` on location fluents in drawn preconditions, the quota `same_rules`, the location statistics, and `locations: 1` in the full worlds) must know:

1. **Where the dynamics live.** A place event type's dynamics are `PlaceEventType.precondition`, `effects`, and `explicit` (`places.py`); `place_dynamics.py` applies an event file's entries after the entity event types are generated and `check_place_dynamics` holds the rules as invariants; `EventTypeRecord.performable` reads the record. Stage c3b draws the dynamics of every place event type without an entry from `world:place_dynamics` (created after `world:habitats`) in the same place, before the definition is built: the kind at `move_share`, the location fluent among `pair_fluents.locations`, the compiled `move` literal or the `act` literal by `compiled_literals` and `ACT_ORIGIN`, and the further literals and effects on the agent.
2. **The entity event types' machinery** (`_Dynamics` in `event_types.py`) draws over `EventType` drafts with `_Draft`, keyed by `self.drafts`; place event types are `PlaceEventType` records of `Places`, outside it. Drawing a place event type's further literals and effects "as for the other event types" means either adding its drafts to `_Dynamics` (with the agent as the only role that has fluents, `SOMEOF` of the place as the one patient literal, and no pair effect between entities) or a small drawer in `place_dynamics.py` that reuses `_draw_literal` and `_draw_effect` over the role `agent`; the checker is ready for either.
3. **The literal forms** on a location fluent are `location_literal_problem` in `definition.py`; `random_pair_literal` draws over `pair_fluents.between_entities` alone, so the quota `same_rules` and the place event types' `pair`, `same`, and `someof` draws on location fluents need their own draw (`PAIR_KIND` and `PAIR_SOMEOF` of the patient for place event types, `PAIR_SAME` for two-place event types), from their own parts of `world:pair_preconditions` or from `world:place_dynamics`; `pair_literal_achievable` already says every such literal is achievable, and `fixed_pair_literals` what a positive `SAME` fixes.
4. **The quota** draws among two-place event types for which some able binding can satisfy the rest of the precondition: `_Dynamics.able_bindings` and `_static_satisfiable` give the able bindings; the literal is `SAME.PAIRFL.k(agent, patient)` on a location fluent, keyed by `pair_literal_key` like every other.
5. **The achievability pool** of the entity event types does not see the place event types' effects (open question 8); if c3b wants an act's effect to enable an entity literal, the pool must be widened before the entity draws, which changes the draws of every world with acts.
6. **Conditions.** An act's or a move's further effects may carry conditions on the agent (feature, fluent, numeric) and `SOMEOF` of the place, never on the place's features (open question 4); `_draw_condition` draws the feature kind over the roles of the event type, so a drawer for place event types must restrict the roles of feature, fluent, and numeric literals to the agent.
7. **The statistics** (open question 7): the `places` block gains the moves and acts and the concentration of habitats; `pair_fluent_stats` should count location fluents apart from the pair fluents between entities and count the place event types' literals and effects; `episode_stats` the move share, the act share, and the two-place share counting place event types apart (`HistoryEvent.type` and `EventTypeRecord.move`/`act` tell them apart).
8. **The habitats** come from `locations.py`: `habitat_weights` (from the requirement matrices, which `Places.requirement` and `place_able_table` both give), `draw_places`, `with_location_fluents`; the episode generator's `habitat_weights` property computes the same weights from the runtime for the redraw. The concentration of habitats for the statistics is a function of `entities.csv`'s location columns and the taxonomies' leaves.
9. **The full worlds.** `locations: 1` in `tiny_full.yaml` and `default_full.yaml` moves their identities (the location symbol), their `pair_fluents` figures, every baseline of theirs (`pair_fluents_off` sets `locations: 0` already), and the `tiny_full` fixtures (`make-fixtures data/world/tiny_full.yaml`, which now writes `initial_places`); a `locations_off` setting (`pair_fluents: {locations: 0}`) with its baselines would test that the world without location fluents is the world of c2b. WM.62 changes `tiny.yaml`'s place requirements, which moves the tiny world's identity, every tiny fixture, the tiny corpus, and their snapshot figures; `tiny_full.yaml` must copy the change (the test that the two files differ in the `pair_fluents` block alone).
10. **The fixtures README** has the location semantics for the Rust runtime ("Location fluents (stage c3a)"); c3b adds nothing to the format unless it draws a new kind of literal.
11. **`view`** ignores the location column of `entities.csv` (a text column); `--include PAIRFL` would add it as text.
