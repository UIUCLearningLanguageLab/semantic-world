### How the pieces stand today

A `Definition` holds the literal table, the entity rules (derived static features and derived fluents) and the binding rules (constraints and requirements) in Boolean form, and both scopes in matrix form. Its literal matrices are filled from a live taxonomy run. Nothing reads `definition.json` back. `RuleMatrices.from_record` rebuilds the layers of one scope from the `literals` and `layers` tables. Binding literals read the entities' derived static features as well as the free ones (`agent.PROPERTY.7`), so the runtime must compute the static derived facts before any requirement. The event-type records carry the requirement's output label, the precondition's literals (role, fluent, value), and the effects (role, fluent, value).

### Plan for the stage

1. **A loader** in `definition.py`: `RuntimeDefinition`, built from the JSON record and the entities table alone, never from a `TaxonomyResult`. It recomputes the rule-set identity from the four tables and refuses a record whose identity differs. `Definition.runtime()` gives the same object from a built definition, so the two paths can be compared.
2. **`runtime.py`**: `State`, `Event`, `DerivedFacts`, and the five operations `derive`, `able`, `legal`, `legal_bindings`, and `apply`, over the matrix layers, vectorized over every given entity or binding at once.
3. **`fixtures.py`**: the brute-force evaluator (truth tables only, one entity or binding at a time, in plain Python), the fixture format, the fixture checker, and the fixture generator.
4. **Fixtures** in `tests/fixtures/world/`: the hand-written cases, then generated fixtures from the tiny world.
5. **`check-fixtures`** and `make-fixtures` on the command line, tests in `tests/world/`, and the documents.

### Reading of the scope

- `derive`, `able`, and `legal` evaluate the matrix layers (REL.18). Only the brute-force evaluator reads truth tables.
- Boolean fluents only. Numeric fluents and conditional effects are phase (b).
- The runtime draws nothing and chooses nothing. The fixture generator and the random-state tests use their own seeded NumPy generator. No world stream is added.
- Every file the taxonomy and the corpus write today stays byte-identical. The stage adds files and commands and changes no output format. The change to the default world's taxonomy (Jon's ruling 3 on stage a2) changes the default world run, not any taxonomy or corpus output.

## Engineering choices

Each choice is numbered. The log in `docs/DECISIONS.md` refers to them as WM.E42 and following (WM.E41 records Jon's change to the default world's taxonomy).

1. **The loader.** `RuntimeDefinition` in `definition.py` is the definition as the runtime reads it. `runtime_definition(record, entities)` builds it from the `definition.json` record and the rows of `entities.csv` (with or without the fluent columns); `load_definition(folder)` reads the two files. The loader validates every reference between the tables (literal kinds and roles, rule scopes and outputs, the layers against the rules, event-type roles, preconditions on fluents, effects on base fluents, the columns of the entities table), recomputes the rule-set identity from the four hashed tables, and refuses a record whose identity differs, with `DefinitionError`. `Definition.runtime()` builds the same object from a built definition through its JSON form, so the two paths can be compared; a test checks that a run folder loads to the same identity and the same arrays.
2. **Indices at the core, labels at the edges.** The runtime refers to entities by their index in the entities table. A binding is a tuple of indices in role order, an `Event` is an event-type label and a binding, and a `State` is a read-only uint8 matrix of every entity's base fluents (entities by base fluents in symbol order). `Event.from_labels`, `State.from_true`, `State.true_fluents`, `DerivedFacts.true_fluents`, and `Event.describe` translate to and from labels. Two states are equal when their matrices are.
3. **Static facts cached once.** `static_facts(definition)` fills the entity literal matrix with the free features and the threshold literals, evaluates the entity layers once, and keeps the matrix (with the derived static columns written in) and every static feature's column, free and derived, on the definition. `derive` copies the rows of the given entities, fills the base fluent columns from the state, and evaluates the entity layers; its derived static facts come from the cache. `able` fills the binding literal matrix from the static columns, the scalars, and the comparisons, and evaluates the binding layers. Nothing reads a truth table. The requirement itself is not cached ("the result can be cached" in the spec is permission, not an instruction); stage a4 can add a per-event-type table over all pairs if episodes need it.
4. **One-place bindings.** The binding literal matrix has columns for both roles. For a one-place event type, the patient's literals and the comparisons stay 0; a one-place requirement never reads them, as the a2 construction guarantees.
5. **The order of `legal_bindings`.** By agent, then patient, in the order of the entities table, whatever order the given entities are in; duplicate entities in the given list collapse. For a two-place event type, the candidates are every ordered pair of distinct given entities.
6. **The errors of `apply`.** `StepError` has a `kind`, the name the fixtures use. `IllegalEventError` (kind `illegal`) covers an unknown event type, a category of event types, a binding with the wrong number of entities, an unknown entity, an entity used twice, a false requirement, and a false precondition literal; the message names the event (`EVENTTYPE2.1.2(agent=INSTANCE.1.1.1, patient=INSTANCE.1.2.1)`) and the reason, down to the literal and the fluent's value. `InterferenceError` (kind `interference`) covers the same fluent of the same entity written by both events, a write to a base fluent in the read cone of the other's precondition, and the same event twice; the message names both events, the fluent, and the entity. Every event's legality is checked before any pair's interference, and pairs are checked in list order.
7. **The fixture format.** Beyond the spec's `definition`, `initial`, `steps`, and `error`: `version` (1), `name` (the file's stem), `description`, and `rule_set_id`; and the `entities` table Jon asked for, one object per entity with `label`, `leaf`, every free feature, and every scalar (the columns of `entities.csv` without the fluents, which `initial` carries). Bindings are `{role: entity label}` objects. `legal` lists every event type of kind `event_type`, never a category, with `[]` when none is legal. `error` is `{"step": k, "kind": ...}` with k counted from 1, as the spec counts steps; the error step is the last step, and holds `events` and `legal` only. Fixtures are written in the indented JSON form with the definition's key order, so they can be read and diffed.
8. **What `check-fixtures` checks.** The fixture's `rule_set_id` against the identity recomputed from the inline definition (and the loader checks the definition's own); the agreement test on the inline definition over the fixture's entities, so a hand-written layer that disagrees with its truth table is caught; `legal` of every event type as ordered lists; then `apply` and, after a step without an error, `state` and `derived`. The first disagreement names the fixture, the step, and what differed. The command prints one line per fixture and exits 1 on the first failure.
9. **The hand-written fixtures.** Twelve files, `hand_01_no_event` to `hand_12_duplicate_event`, over one hand world of three entities (`PROPERTY.1` free, `PROPERTY.2 = NOT PROPERTY.1`, `SCALARDIM.1`, base `BOOLFL.1` and `BOOLFL.2`, derived `BOOLFL.3 = BOOLFL.1 AND BOOLFL.2`, event types `EVENTTYPE1.1` to `EVENTTYPE1.3` and `EVENTTYPE2.1`, whose requirement has a comparison). The spec's eight cases are files 1 to 8; files 9 to 12 add the same fluent written twice, interference through the cone of a derived fluent (the two events write different fluents), a false requirement, and the same event twice. Every expected value was worked out by hand; the identity, which cannot be, was computed by the tool. The runtime caught one slip in the hand work (an entity that is not able for an event type was listed as legal), which was corrected by hand.
10. **The generated fixtures and `make-fixtures`.** `python -m semantic_world.world make-fixtures CONFIG [--out FOLDER] [--count N] [--steps N]` defines the world in memory and writes `count` fixtures of `steps` random steps (fixture seeds 1 to `count`), then one that ends in an illegal event and one that ends in interfering events (fixture seed `count + 1`). At each step the generator takes a random target of 0 to 3 events and adds legal events in a random order while they do not interfere; the error steps draw from the events that are illegal, or the pairs of legal events that interfere, in that state. The committed `tiny_*` files are `count` 4 and `steps` 6, and a test regenerates them in memory and requires the committed files byte for byte, so the fixtures cannot drift from the tiny world.
11. **The brute-force evaluator.** `BruteForce` in `fixtures.py` works in plain Python over the definition record and the entities rows: a rule is a truth-table lookup at the setting of its inputs (first input most significant), and a literal is evaluated by its definition, recursing into derived features, derived fluents, and constraints. It has its own `able`, `legal`, `legal_bindings`, cones, interference test, and `apply`, written from the spec's text, and reads the layers nowhere. The random-state test compares the runtime's `derive` and `legal_bindings` with it in 1,000 random states, and the order-independence test uses its interference test to draw non-interfering sets.
12. **The agreement test over a loaded definition.** `check_definition_agreement(definition)` in `runtime.py` runs the agreement test of REL.18 on a `RuntimeDefinition`: every entity rule on every entity (with the initial fluents when the entities table has them, else zeros) and every binding rule on every ordered pair, and the exhaustive check of rules with at most 12 inputs. It lives in `runtime.py` because it needs the runtime's literal matrices, and `definition.py` cannot import `runtime.py`.
13. **No new stream.** The fixture generator and the random-state tests draw from `numpy.random.default_rng` with fixed seeds (the fixture seed, and literal seeds in the tests). The runtime draws nothing. No world stream was added, as Jon's brief says.
14. **The README.** `tests/fixtures/world/README.md` describes the fixture file, the definition record, the canonical JSON and the identity (key order, the absence of whitespace, the ASCII escapes, `%.17g` floats with `.0` appended, and which fields are floats), literal values, the evaluation of the layers, and the semantics of each operation, for whoever builds the Rust runtime.

## Open questions

None blocks the stage. Each is an easy change in stage a4.

1. **Caching `able`.** Should the runtime keep, per event type, the requirement over every ordered pair of entities (choice 3), so that episodes over a pool of participants never recompute it? The tiny and default worlds (12 and 284 entities) do not need it yet.
2. **The error step's number.** `error.step` counts from 1, as the spec counts steps (choice 7). Is that the count Jon wants, or should it be the index into `steps`?
3. **The `entities` table of a fixture** leaves the fluent columns to `initial` (choice 7). Should it carry the full rows of `entities.csv` instead, with `initial` repeating them?
4. **The hand world's generator script.** The twelve hand fixtures were assembled by a short script outside the repository (the hand world once, the cases by hand). Should the script be committed, for example as `tests/world/hand_world.py`, so the hand world can be extended?

## Jon's rulings (October 8, 2026, in the stage a4 prompt)

Choices 1 to 14 are approved. The open questions are answered:

1. **Caching `able`**: yes. The requirement is computed once per event type over all ordered pairs, on first use, and reused (`able_table` in `runtime.py`, stage a4).
2. **The error step's number**: counting from 1 is approved, as the spec numbers steps.
3. **The `entities` table of a fixture** keeps leaving the fluent columns to `initial`.
4. **The hand world's script** is committed as `tests/world/hand_world.py`. It builds the hand world and the cases. The expected values stay typed in by hand, never computed by the runtime or the brute-force evaluator.

From Jon's review: every fixture, hand-written or generated, must pass both the runtime and the brute-force evaluator. Stage a4 adds that test. The hand values of fixture 5 were corrected to match the runtime, so they need this independent check.
