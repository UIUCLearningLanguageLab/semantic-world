### How the pieces stand today

CAN rules are sampled by the taxonomy's rule builder from the `taxonomy:rules` stream, after the IS and HAS rules, and the same stream also draws the layer assignment and every threshold. Verbs, constraints, projections, and relation statistics are built by `generate_relations`, `compute_projections`, and `compute_relation_stats` from the `verb_tree`, `constraints`, and `pairs` streams, after the noun tree and the instances. All of this is reachable from one call, `semantic_world.taxonomy.generate(config)`, whose result holds the live objects.

### Plan for the stage

1. **The world embeds a taxonomy run.** `define` builds the taxonomy configuration from the world configuration (the file named by `taxonomy.config`, the world's seed unless `taxonomy.seed` is given, and the `event_types.unary` and `event_types.binary` blocks merged over the taxonomy's `features.can` and `verbs` blocks), runs `semantic_world.taxonomy.generate`, and writes the result to `taxonomy/`. One-place event types take their requirements from the CAN rules of that result; two-place event types take their constraints, capacities (the projections), and relation statistics from it. Equal draws are therefore exact, not approximate: the world's requirements, capacities, and relation statistics are the taxonomy's own objects, relabeled.
2. **Labels are translated in one module**, `world/labels.py`, from the taxonomy's current labels to the labels of the spec's "Labels" section, in every file the world writes, and back for parsing expressions in the event file. Stage a5 removes the translation.
3. **New modules**: `config.py`, `streams.py`, `labels.py`, `fluents.py`, `event_types.py`, `preconditions.py`, `effects.py`, `event_file.py`, `definition.py`, `capacities.py`, `relation_stats.py`, `stats.py`, `views.py`, `generate.py`, and `__main__.py`, as the spec's module table suggests.
4. **Two-place requirements in matrix form**: each constraint is a rule over binding literals (`agent.PROPERTY.3`, `patient.SCALARDIM.1 > 0.4127`, `agent.SCALARDIM.1 - patient.SCALARDIM.1 > 0.15`), and one more rule per event type ANDs its constraints' outputs. The agreement test covers every constraint and every requirement over every ordered pair of entities, and every rule with at most 12 inputs on every input setting.
5. **Tests** in `tests/world/`, including the equality of requirements, capacities, and relation statistics with the taxonomy's for the same seed, and the regression tests of stage a1.

### Reading of the scope

- World statistics from 1,000 episodes need the runtime (stage a3) and episodes (stage a4). `world_stats.yaml` in this stage reports everything else in "World statistics": the counts, the dropped effects, the enabling graph, and the absorbing fluents. Stage a4 adds the episode statistics.
- The event file can give requirements as well as preconditions and effects. A requirement in the file replaces the event type's own constraint (for a two-place event type) or its CAN rule (for a one-place event type), and the capacities and relation statistics of the affected event types are recomputed with the taxonomy's own functions. `data/world/events/chain_example.yaml` gives preconditions and effects only, as the spec's example does.

## Engineering choices

Each choice is numbered. The log in `docs/DECISIONS.md` refers to them as WM.E18 and following.

1. **The world embeds a taxonomy run.** `define` builds the taxonomy configuration from the world configuration and runs `semantic_world.taxonomy.generate`. One-place requirements are the CAN rules of that run, two-place requirements its constraints, capacities its projections, and the relation statistics its statistics, all relabeled. So "with `fluents.count: 0` and the old settings moved over, requirements, capacities, and relation statistics equal what the taxonomy computes today" holds exactly, by construction, for every seed, and a test checks it. The unmodified run is written to `taxonomy/`.
2. **The moved settings are overrides.** `event_types.unary` takes `count` (the taxonomy's `features.can.count`) and `rules` (its `rules.overrides.can`, the sampling overrides for CAN rules). `event_types.binary` is the old `verbs` block, merged key by key over the `verbs` block of the taxonomy file; `null` turns two-place event types off, and `{}` turns them on with the taxonomy file's settings or the defaults. The exposure keys (`projections`) are rejected with an error that points to views. The taxonomy's seed is the world's unless `taxonomy.seed` is given, and `taxonomy.config` is read as written (relative to the current directory, as the corpus reads it).
3. **Labels are translated in one module**, `world/labels.py`. `translate` maps a symbol (`C1.2` to `CATEGORY.1.2`, `CAN.3` to the event type `EVENTTYPE1.3`, `K.VF.4` to `CONSTRAINT.EVENTFEAT.4`); `capacity_label` and `translate_column` map table columns (`CAN.3` to `CAN.EVENTTYPE1.3`, `CANBE.V1.2` to `CANBE.EVENTTYPE2.1.2`); `translate_expression` maps every label token of an expression or a literal key, with `a.` and `p.` becoming `agent.` and `patient.`; `untranslate` goes back for parsing with the taxonomy's tools. Stage a5 removes the module.
4. **Configuration errors are the taxonomy's `ConfigError`**, which names the file and the field, read through the taxonomy's `_Node` reader. A run's `config.yaml` holds the resolved taxonomy configuration under `taxonomy.resolved`, which the loader accepts and ignores, and `provenance.stream_seeds` lists the taxonomy's streams and the world's.
5. **Fluent numbering and layers.** Base fluents come first and derived fluents last; the derived count is the round-half-up of `count × derived_proportion`; derived fluents are split evenly over layers 1 to `max_chain_depth`, lowest first. Fluents named in an event file are base fluents, and the derived fluents are the last of the rest. On `world:fluents`, every base fluent's initial rate is drawn first (a uniform choice from `initial_rates`, overwritten by the event file's rate when given), then every derived rule. `world:initial` draws the initial values.
6. **Derived fluent rules.** The input pool holds the fluents of lower layers (weight 1), the static IS and HAS features (by the taxonomy's `rules.input_type_weights`), and the scalars (by the scalar weight); the first input is a fluent of the layer below, drawn uniformly; the function comes from the taxonomy's `build_function` with the taxonomy's `rules` settings; thresholds are drawn as the taxonomy draws them; a duplicate function of the same inputs is redrawn unless `rules.allow_duplicate_rules`.
7. **Draw order of the dynamics.** Effects first, on `world:effects`: each one-place event type's own effects, each event-type feature's effect (with `feature_rate`), each two-place event type's own effects. Then preconditions, on `world:preconditions`, in the same order. One-place event types always use the role `agent`; two-place roles come from the configured weights. Effects write base fluents only. Categories carry only the effects and literals of their defining features.
8. **Fix-ups.** Among inherited effects (and literals) with the same role and fluent, the lowest-numbered feature's is kept and the others are dropped, as contradictions or duplicates. An own effect or literal whose role and fluent are already taken is redrawn. An effect that sets a fluent to the value the precondition requires is redrawn when own and dropped when inherited. A literal that is not achievable is redrawn when own and dropped when inherited. The fix-ups repeat until nothing changes (at most 20 rounds), and every count goes to `world_stats.yaml` under `fix_ups`.
9. **Achievable** includes the initial values of derived fluents, computed from the initial state by truth-table lookup.
10. **Explicit entries replace the sampled dynamics** of the event type they name: a `precondition` or `effects` key given in the file is the whole precondition or the whole set of effects, inherited terms included. An entry on an event-type category is an error. Explicit literals are checked for achievability after everything is drawn, and an unachievable one is an error that names the file and the entry.
11. **Explicit requirements** replace a one-place event type's CAN rule, or a two-place event type's own constraint (the inherited feature constraints stay), in `world/requirements.py`. The affected derived values are recomputed with the taxonomy's own functions: the CAN column, the node vectors, the projections, and the relation statistics (from a fresh `taxonomy:pairs` generator). The unmodified run still goes to `taxonomy/`.
12. **One literal table, two scopes.** Entity literals have `role: null` (features, thresholds, fluents). Binding literals have the role `agent` or `patient` (features, thresholds), or `binding` (a comparison between the two roles' scalars, or a constraint's output). A constraint's output is a literal, so the requirement rule can read it. The table is ordered by group (entity features, thresholds, fluents; agent features, thresholds; patient features, thresholds; comparisons; constraints), then by position or label.
13. **Constraints and requirements are rules.** The `rules` table lists every rule output with a `scope` (`entity` or `binding`) and a `family`: derived static features and derived fluents (entity), constraints and the requirement `REQUIREMENT.<event type>` that ANDs an event type's constraints (binding, family `requirement`). Each `layers` entry carries its `scope`. The identity therefore covers the constraints through `rules`, and the four tables of the spec stay the hashed tables.
14. **Symbol kinds** are `property`, `part`, `scalar`, `fluent`, `event_type`, and `event_type_category`, following the new labels rather than the spec's older `is` and `has`. Event-type features and constraints are not symbols; they appear in the event types' `features` and `requirement`.
15. **Event-type records** hold `label`, `kind`, `arity`, `roles`, `parent`, `level`, `features`, `explicit`, `requirement` (`constraints`, `output`, `expression`), `precondition` (`literals` as role, fluent, value; and the `expression`), and `effects` (role, fluent, value, `expression`).
16. **`entities.csv`** has `label`, `leaf`, the free PROPERTY and PART features, the scalars (full precision), and the initial base fluents. The derived tables keep the taxonomy's six-decimal floats.
17. **The agreement test over bindings** runs in chunks of agents against the taxonomy's own evaluation of each constraint, with every requirement checked as the conjunction, and the exhaustive check of input settings once. `check_dynamics` re-checks every rule of "Preconditions" and "Effects" at the end of every run, and a violation fails the run.
18. **`derived/`** holds `static_features.csv` (relabeled), `capacities.csv` (the one-place capacities from the CAN features, then the two-place intensional capacities, the `approximate` column, and the extensional capacities), `capacity_roles.csv` (`category`, `event_type`, `status` in `fixed_1`, `fixed_0`, `free`, and `test` in `exact`, `local`, or empty), and the four relation files with the `verb` column renamed `event_type`.
19. **Views.** `label` and `leaf` are always the first columns. A prefix in `--include` that matches columns of the preset narrows the view to them; a prefix that matches none adds every available column with that prefix (ISA, base facts, derived static features, capacities, initial fluents). The default output is `RUN/views/<preset>.csv` with the sidecar beside it as `.yaml`; ISA columns come from `taxonomy/tree.csv`.
20. **`world_stats.yaml`** reports the structural statistics now and `episodes: null` until stage a4. The longest chain of the enabling graph is measured over the graph's strongly connected components, so a cycle counts as one step.
21. **Data files**: `data/world/default.yaml`, `data/world/tiny.yaml` (the tiny relations taxonomy with 4 fluents), `data/world/tiny_chain.yaml` (the tiny world with the chain example), and `data/world/events/chain_example.yaml`. `event_file` is resolved relative to the configuration file's folder, as `rules.file` is.
22. **Streams** `world:fluents`, `world:initial`, `world:preconditions`, `world:effects`, and `world:stats`, seeded by the taxonomy's function; `world:stats` is reserved for stage a4.
23. **Modules.** `dynamics.py` holds the `Literal` and `Effect` classes; their generation lives in `event_types.py`, so the spec's `preconditions.py` and `effects.py` are one module with the event-type tree they attach to. `requirements.py` holds choice 11.

## Open questions

None blocks the stage; each is an easy change in stage a3.

1. **Symbol kinds** (choice 14): `property` and `part`, or the spec's `is` and `has`?
2. **Constraints as rules** (choice 13): keep them in `rules` with a `scope`, or give `definition.json` a `constraints` table of its own (which the identity would then have to cover as a fifth table)?
3. **The default of `binary`** (choice 2): `{}` turns two-place event types on even when the taxonomy file has `verbs: null`, so the default world on `data/taxonomy/default.yaml` has seven two-place event types. Is that the intended default?
4. **Explicit entries and inheritance** (choices 10 and 11): an explicit precondition or set of effects replaces the inherited terms, while an explicit requirement keeps the inherited feature constraints. Should the two behave alike?

## Jon's rulings (October 8, 2026, in the stage a3 prompt)

Choices 1 to 23 are approved. The open questions are answered:

1. **Symbol kinds** (choice 14): `property` and `part` stay.
2. **Constraints as rules** (choice 13): constraints and requirements stay in `rules` with a `scope`. No `constraints` table is added.
3. **The default of `binary`** (choice 2): `{}` turning two-place event types on is approved. But the default world must use the taxonomy that today's default corpus uses: `data/world/default.yaml` now reads `taxonomy: {config: data/taxonomy/relations.yaml, seed: null}`, and the same default is hard-coded in `python/semantic_world/world/config.py`, so the comment in `default.yaml` that every value shown is a default stays true. With `relations.yaml`, the default world has scalars and the corpus's verbs, and its requirements gain threshold literals and comparisons. The tests that read the default world were checked against the new file (stage a3).
4. **Explicit entries and inheritance** (choices 10 and 11): the asymmetry is kept, on purpose. An explicit requirement keeps the inherited feature constraints, because every event type must entail its ancestors' base relations (REL.10), and the corpus relies on this when it names an event at a higher level of the event-type tree. An explicit precondition or set of effects replaces the inherited terms, because the inheritance of preconditions and effects is a sampling convenience, not a semantic commitment.

The statistics from 1,000 episodes arrive in stage a4, as the reading of the scope says.
