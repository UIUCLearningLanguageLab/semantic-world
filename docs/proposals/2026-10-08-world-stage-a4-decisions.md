### How the pieces stand today

Scenes draw participants from the taxonomy's leaf-pair thematic relatedness and similarity, and events from a static pool, verb first. The world run writes the same leaf-pair numbers to `derived/thematic.csv` when it has two-place event types, and the entities' leaves to `entities.csv`. The runtime gives `legal_bindings` and `apply`, and `RuntimeDefinition` loads from a run folder, so episodes can run from the files alone. `define` builds `world_stats.yaml` with `episodes: None`.

### Plan for the stage

1. **Episode settings** in `episodes.py`: the scene settings with the corpus's defaults, read from the `scene` block of a corpus configuration file when `--config` is given (`size`, `steps`, `events_per_step`, `transitive_share`, `participant_weights`, `verb_weights` with the old labels translated, and the new keys `event_type_weights`, `policy`, `initial`).
2. **Relatedness**: the leaf-pair thematic and similarity matrices and each entity's leaf, from `derived/thematic.csv` and `entities.csv`, or in memory from the taxonomy result.
3. **`policies.py`**: a registry, the shared notion of the available events (legal in the state and not interfering with the events already chosen), `uniform_event`, and `uniform_event_type`.
4. **`history.py`**: the history schema, reading and writing `episodes.jsonl`, and `replay`.
5. **`episodes.py`**: participants, initial state (kept or redrawn), steps, quiescence, each episode from its own part of a stream.
6. **The runtime**: `able` cached per event type over all ordered pairs on first use (Jon's ruling 1 on stage a3).
7. **`simulate`** on the command line, the episode statistics in `world_stats.yaml`, the fixtures test against the brute-force evaluator, `tests/world/hand_world.py`, tests, and the documents.

### Reading of the scope

- Episodes draw from `world:stats` (the statistics) or `world:episodes` (`simulate`), each episode from its own part named by its label, with the seed instance drawn first from the part when the caller gives none. The corpus (stage a5) will give the seed instance itself, as the planner does now.
- `corpus/scenes.py` is untouched. Nothing the taxonomy or the corpus writes changes.
- Histories hold Boolean changes (`to: true | false`); phase (b) adds numeric changes with their causes.

## Engineering choices

Each choice is numbered. The log in `docs/DECISIONS.md` refers to them as WM.E56 and following.

1. **The scene settings and `--config`.** `EpisodeSettings` in `episodes.py` holds the corpus's scene settings with the corpus's defaults (`size: [2, 6]`, `steps: [3, 8]`, `events_per_step: 1.5`, `transitive_share: 0.5`, `participant_weights: {thematic: 1.0, taxonomic: 0.5, constant: 0.1}`, uniform event-type weights, `policy: uniform_event`, `initial: keep`). `simulate` runs with the defaults, or with `--config CORPUS.yaml` reads the `scene` block of a corpus configuration file through the taxonomy's `_Node` reader: the corpus's keys, `verb_weights` with its old labels translated (`CAN.1` to `EVENTTYPE1.1`), and the keys the corpus does not know yet, `event_type_weights` (new labels), `policy`, and `initial`. Unknown keys, unknown event types, and bad values are `ConfigError`s that name the field. The corpus itself still reads only its own keys until stage a5.
2. **Streams and parts.** `simulate` draws from `world:episodes` and the statistics from `world:stats`; each episode draws from its own part, `<stream>:SCENE.<n>`, with the seed function of `semantic_world.taxonomy.streams`. The seed instance is the first draw of the part (uniform over the entities) when the caller gives none; the corpus will give its own, as the planner does now. `simulate`'s master seed defaults to the run's seed (`config.yaml`). `world:episodes` is not in `WorldStreams.STREAM_NAMES`, so a run's `config.yaml` is unchanged.
3. **The draw order of an episode's part**: the seed instance (when drawn), the participants (the size, then the weighted choice without replacement, as the corpus draws them), the number of steps, the initial redraw (when `initial: redraw`), then for each step the Poisson count and the policy's draws. A later setting never changes an earlier draw.
4. **Relatedness.** Thematic relatedness comes from `derived/thematic.csv` (0 everywhere for a world without two-place event types), through the manifest's identity check. Taxonomic similarity is always computed from the leaves' generative vectors with the taxonomy's `analysis.similarity_metric` and `similarity_features`, exactly as `corpus/scenes.py` computes it: in memory from the taxonomy result, and from a run folder from `taxonomy/categories_generative.csv` (the ISA, IS, HAS, and CAN columns) and `taxonomy/config.yaml`. `thematic.csv` lists only some leaf pairs, so its `similarity` column is not used. A test checks that the weights and the drawn participants equal the corpus scene generator's for every seed instance of the tiny world, and that a run folder gives the same relatedness as memory.
5. **Policies.** A policy is a function of a `StepContext` (the definition, the state, the participants, the legal bindings of every event type among them, the event-type weights, and the transitive share), its generator, and the number of events to draw; it returns the events. `StepContext.available(chosen)` gives the legal events that do not interfere with the events already chosen (`runtime.interferes`, the same test `apply` makes). Policies are registered by name with `register`, looked up with `policy`; an unknown name is an error that lists the names. An event type with the weight 0 is never drawn, as a verb with the weight 0 was.
6. **`uniform_event_type` mirrors the corpus's draw**: the kind of event is one-place when the share is below 1 and a one-place event is available, two-place when the share is above 0 and one is available, and by one draw against the share when both are; then the event type by weight among those with an available event; then a binding uniformly. `uniform_event` draws among all available events, each weighted by its event type's weight.
7. **Histories.** `history.py` holds `Change`, `HistoryEvent`, `Step`, and `History`, with the schema of "Histories": `patient` is left out of a one-place event; `changes` lists the event's own written fluents whose value changed (an effect that sets a fluent to its value records nothing); `legal` is written per step only with `--legal`; `final` is `TIME.<steps + 1>`. `replay` runs the events through `apply` from the initial state (participants from the history, every other entity from the definition's initial values), and requires that the recorded changes are exactly the base fluents that changed and that each change belongs to an effect of its event; a history replays only on the definition with its `rule_set_id`.
8. **Quiescence** is tested at each time point before the Poisson draw: when no event type has a legal binding among the participants, the episode ends there with the steps so far and `quiescent: true`. A step whose Poisson count is 0, or whose draws find nothing available, is recorded with no events.
9. **`able` is cached** (Jon's ruling 1 on stage a3): `able_table` evaluates the binding layers once over every entity (one-place) and every ordered pair in chunks of 32,768 (two-place) on first use, and keeps every event type's requirement on the definition; `able` indexes the table. The precondition check derives over the bound entities only. The default world's table takes about one second; `define` on the default world, with its 1,000 statistics episodes, takes about five seconds.
10. **The statistics episodes.** `define` runs 1,000 episodes of the default policy with the default settings on `world:stats`, seeded with the world's seed, and `world_stats.yaml` reports them under `episodes`: `count`, `steps`, `events`, `legal_share` and `occurrence_share` per event type (the share of steps at which it had a legal binding among the participants, and at which it occurred), `mean_changes_per_event`, `quiescent_share`, `never_legal`, and `warnings`. The tiny world's statistics are reproduced by a test from the same stream.
11. **Initial rates in `world_stats.yaml`.** A run recorded no base fluent's initial rate (the configuration lists the candidate rates only), and `scene.initial: redraw` needs them. `world_stats.yaml` now reports `fluents.initial_rates`, and `simulate` reads them from the run; without them, `redraw` is an error that names the fluent. This is the one addition to a world file, flagged as open question 1.
12. **Every fixture passes the brute-force evaluator too** (Jon's review): `check_fixture_brute` runs the evaluator through a fixture apart from the runtime (the legal bindings before each step, the error step's kind, the state and the derived fluents after each step); `check-fixtures` runs it after the runtime on every file, and a parametrized test does the same.
13. **`tests/world/hand_world.py`** (Jon's ruling 4) holds the hand world and the twelve cases, with every expected value typed in by hand; it assembles the files and fills in the identity. A test loads the module by path and requires the committed files to equal its output byte for byte.
14. **Definitions without initial values.** A definition whose entities table has no fluent columns (a fixture's) has `initial_values` None, except that a world with no base fluents gets an empty matrix; episodes on such a definition need `initial: redraw`, and `replay` starts its other entities with every fluent false.
15. **`simulate` writes `RUN/episodes.jsonl`** by default, or `--out FILE`; the command prints the episode, event, and quiescent counts and the policy.

## Open questions

None blocks the stage. The first is the one that touches a file's content.

1. **Where the initial rates live** (choice 11). A run must record each base fluent's initial rate for `scene.initial: redraw` to work from the files. Options: (a) `fluents.initial_rates` in `world_stats.yaml`, as built now; (b) a new table `fluents.csv` in the run folder (label, base or derived, layer, initial rate), which would also give readers the fluent layers; (c) a field of the fluent symbols in `definition.json`, which would put the rate into the rule-set identity. Recommendation: (b) at stage a5, when the run folder is regenerated anyway, and (a) until then; never (c).
2. **The chain example's seed.** With seed 1, the sampled requirements of `tiny_chain.yaml` make no entity both catchable (a patient of `EVENTTYPE2.1.1`) and eatable (a patient of `EVENTTYPE2.1.2`), so the chain never completes, and eatings happen only because sampled event types also set `BOOLFL.2`. The test checks the forced order on seed 1 and the strict chain on seed 3, where six patients overlap. Should the worked example give the chain's requirements explicitly (the event file can), so the chain completes on every seed? Recommendation: yes, at stage a5, as world content for Jon to write.
3. **`world:episodes`** is a stream name that `WorldStreams` does not list (choice 2). Should it join `STREAM_NAMES`, so a run's `config.yaml` records its seed under `provenance.stream_seeds`?
4. **Seed instances of `simulate`.** Each episode draws its seed instance uniformly from its own part (choice 2). Should `simulate` instead cycle through the entities, or take a list, for studies that want every entity seeded?
